# freelance-bot — подробное руководство

Это руководство описывает проект целиком: зачем он нужен, как устроен, как его
настроить, запустить Telegram-бота, читать результаты и расширять код. Оно
рассчитано на человека, который хочет не просто пользоваться ботом, а понять,
как такой бот делается, и повторить его на другом наборе площадок.

Связанные документы:

- [`README.md`](README.md) — краткое описание и быстрый старт.
- [`TELEGRAM.md`](TELEGRAM.md) — практическая инструкция по Telegram-панели.
- [`PROFILE.md`](PROFILE.md) — профиль исполнителя и стиль письма.
- [`DEPLOY_VPS.md`](DEPLOY_VPS.md) — развёртывание на VPS.
- [`REPORT.md`](REPORT.md) — инженерный отчёт и история исследований.
- [`tests/README.md`](tests/README.md) — карта тестов.

## 1. Что делает проект

`freelance-bot` — агрегатор публичных лент заказов на русскоязычных
фриланс-площадках. Он:

1. собирает карточки заказов с включённых площадок;
2. приводит бюджет, валюту, даты и дедлайны к единому виду;
3. убирает дубликаты и запоминает уже виденные заказы в SQLite;
4. при необходимости классифицирует заказ по таксономии Kwork и применяет
   фильтр категорий;
5. считает объяснимый балл по шести факторам и штрафует красные флаги;
6. отбирает заказы, прошедшие порог по баллу и по совпадению навыков;
7. генерирует первое сообщение заказчику через OpenAI-совместимую LLM;
8. проверяет сообщение защитой качества и при необходимости исправляет его;
9. пишет проверяемый артефакт в outbox и/или отправляет карточку в Telegram;
10. хранит заказы, сообщения и историю циклов в SQLite.

Ключевой принцип: **бот не логинится на площадки, не обходит платные стены и не
отправляет сообщения автоматически**. По умолчанию включён `dry_run`: текст
письма рендерится, сохраняется и показывается оператору, но никуда не уходит.
Живая отправка требует явного транспорта и подтверждения каждого сообщения.
Это не «недоделка», а осознанная граница проекта: точки отправки на площадках
закрыты авторизованной сессией, а автоматизация входа выходит за рамки задачи.

## 2. Быстрый старт

### 2.1. Требования

- Python 3.11 или новее (проект проверялся на 3.13).
- Windows, Linux или macOS.
- Для браузерных площадок — Playwright и Chromium.
- Для Telegram — токен бота и ваш chat id.
- Для LLM — любой OpenAI-совместимый endpoint: OpenAI, OpenRouter, локальный
  vLLM и т. п. Ключ не обязателен: без него работает детерминированный
  русский fallback.

### 2.2. Установка (Windows PowerShell)

```powershell
cd C:\Users\StickyFox\Documents\OpenCode_Projects\Project_Parser

python -m venv venv
.\venv\Scripts\Activate.ps1

python -m pip install -e ".[browser,dev]"
python -m playwright install chromium

Copy-Item config.example.yaml config.yaml
Copy-Item .env.example .env
```

### 2.3. Установка (Linux/macOS)

```bash
cd Project_Parser
python3 -m venv venv
source venv/bin/activate
python -m pip install -e ".[browser,dev]"
python -m playwright install chromium
cp config.example.yaml config.yaml
cp .env.example .env
```

### 2.4. Минимальная проверка

```powershell
$env:PYTHONIOENCODING = "utf-8"
$env:FREELANCE_BOT_CONFIG = "config.yaml"

python -m freelance_bot.cli preflight
python -m freelance_bot.cli version
python -m freelance_bot.cli platforms
```

`preflight` проверяет Python, зависимости, режим dry-run, наличие ключа LLM,
прокси, решателя CAPTCHA, путь к базе и outbox. Уровни: `ok`, `warn`, `fail`.
При `fail` команда завершается с кодом 1.

### 2.5. Первый цикл

```powershell
python -m freelance_bot.cli run --top 10
```

Что произойдёт:

- будут собраны включённые площадки;
- заказы сохранятся в `var/freelance.db`;
- письма появятся в `var/outbox/YYYY-MM-DD/`;
- в `var/outbox/messages.jsonl` добавится запись на каждое письмо;
- в консоли появится таблица результатов по площадкам и сводка цикла.

Повторный запуск не должен создавать duplicate-письма: заказы дедуплицируются
по `uid = platform:external_id`, а сообщения — по паре `(job_uid, text)`.

## 3. Архитектура и поток данных

### 3.1. Общая схема

```text
CLI / Telegram loop
        |
        v
pipeline.collect
  -> build_adapters(config)
  -> build_context(config, secrets)
       -> StealthHttpClient
       -> ProxyPool
       -> RobotsCache
       -> BrowserFetcher (если включён)
       -> CaptchaSolver (если есть ключ)
  -> для каждого адаптера: adapter.fetch(ctx)
       -> robots.txt
       -> HTTP/браузер
       -> classify_response
       -> parse(html) -> list[RawJob]
  -> normalise(raw) -> Job
        |
        v
run_cycle
  -> дедупликация внутри цикла по uid
  -> CategoryFilter + classify_job
  -> ScoringEngine.rank (порядок показа, без порогов)
  -> сохранение всех заказов в SQLite
  -> только новые, сортировка: без штрафа, затем по свежести
  -> MessageGenerator.generate
       -> LLM / fallback
       -> guard.check
       -> repair
  -> OutboxSender.send
  -> Telegram deliver_job (личные фильтры -> chat_ids)
  -> notify_cycle_complete
  -> save_cycle
```

### 3.2. Порядок и ответственность слоёв

| Слой | Модуль | Ответственность |
|---|---|---|
| Конфигурация | `config.py` | YAML + `.env`, pydantic-валидация, значения по умолчанию |
| Модели | `models.py` | `RawJob`, `Job`, `ScoredJob`, `GeneratedMessage`, отчёты |
| Адаптеры | `adapters/` | загрузка страницы и извлечение `RawJob` |
| Сеть | `net/` | robots, лимиты, прокси, TLS-имперсонация, браузер, CAPTCHA |
| Нормализация | `normalize.py` | деньги, валюты, даты, дедлайны |
| Категории | `categories.py`, `kwork_taxonomy.py` | дерево Kwork, классификация, фильтр |
| Скоринг | `scoring/` | шесть факторов, красные флаги, порог допуска |
| LLM | `llm/` | промпты, клиент, анализ, письмо, guard, fallback |
| Отправка | `sender.py` | outbox, dry-run/assist/live, rate gate |
| Хранение | `storage.py` | SQLite: заказы, сообщения, циклы |
| Оркестрация | `pipeline.py` | полный цикл и trial |
| Telegram | `telegram_bot.py`, `cli_telegram.py` | панель, уведомления, одобрение |
| CLI | `cli*.py` | команды и отображение |

## 5. Конфигурация

### 5.1. Как выбирается конфиг

`config.load_config()` смотрит:

1. явно переданный путь (`--config`);
2. переменную окружения `FREELANCE_BOT_CONFIG`;
3. файл `config.yaml` в текущем каталоге.

Если файла нет, возвращаются безопасные значения по умолчанию с `dry_run=True`.
`get_config()` и `get_secrets()` кешируются через `lru_cache`, поэтому в одном
процессе конфиг читается один раз. Для тестов это важно: меняйте окружение до
первого вызова или перезапускайте процесс.

### 5.2. `config.yaml`

#### `runtime`

| Ключ | По умолчанию | Смысл |
|---|---:|---|
| `timezone` | `Europe/Moscow` | часовой пояс отображения |
| `dry_run` | `true` | ничего не отправлять, только outbox |
| `poll_interval_seconds` | `600` | интервал цикла по умолчанию (600–3600, меняется через `/interval`) |
| `max_jobs_per_platform` | `40` | остановить пагинацию после N заказов |
| `request_timeout_seconds` | `25` | таймаут HTTP-запроса |
| `user_agent` | Chrome 131 | User-Agent для HTTP и браузера |
| `accept_language` | `ru-RU,ru;q=0.9,...` | Accept-Language |

`poll_interval_seconds` ограничен диапазоном 600–3600 секунд (`clamp_poll_interval`
в `config.py`): значения вне границ обрезаются при загрузке и при изменении через
`/interval`. Команда `/interval` доступна только супер-админу.

#### `network`

| Ключ | Смысл |
|---|---|
| `proxy_strategy` | `round_robin`, `sticky` или `none` |
| `proxy_cooldown_seconds` | базовое остывание прокси после ошибки |
| `respect_robots_txt` | проверять robots.txt перед загрузкой |
| `default_rate` | `requests_per_minute` и `burst` по умолчанию |
| `domains` | переопределение лимитов по домену |
| `backoff` | `base_seconds`, `max_seconds`, `jitter`, `max_retries` |
| `browser` | `enabled`, `headless`, `locale`, `timezone`, `viewport`, `settle_ms`, `navigation_timeout_ms` |

Лимиты намеренно консервативные: 2–4 запроса в минуту на площадку. Не
увеличивайте их без необходимости: это и вежливость, и защита от блокировок.

Для домена дополнительно можно задать `pause_min_seconds` и
`pause_max_seconds`: случайная «человеческая» пауза между запросами поверх
вёдра токенов. Для `kwork.ru` (3–10 с) она включена по умолчанию — антибот
Qrator ругается на частые однотипные запросы. Перед первым запросом к домену
HTTP-сессия автоматически «прогревается»: бот заходит на главную страницу,
получает cookies, и только потом запрашивает листинг; заголовки запросов
(User-Agent, Sec-CH-UA и платформа) всегда согласованы с TLS-отпечатком
профиля. Ответы 429 и 5xx повторяются с экспоненциальной задержкой.

#### `captcha`

| Ключ | Смысл |
|---|---|
| `enabled` | включать решатель |
| `provider` | `capsolver` или `twocaptcha` |
| `solve_yandex_smartcaptcha` | разрешить Yandex SmartCaptcha |
| `solve_recaptcha_v2` | разрешить reCAPTCHA v2 |
| `solve_hcaptcha` | разрешить hCaptcha |
| `max_attempts` | число попыток |
| `timeout_seconds` | общий таймаут решения |

Решатель вызывается только после того, как слой HTTP или браузера **подтвердил**
challenge. Токены не кешируются между сессиями, ключи не логируются.

#### `platforms`

Для каждой площадки:

| Ключ | Смысл |
|---|---|
| `enabled` | участвует ли площадка в цикле |
| `transport` | `http` или `browser` |
| `listing_url` | стартовый URL ленты |
| `detail_enrichment` | зарезервированное поле; сейчас адаптеры его не используют |
| `notes` | пояснение для `platforms` |
| `max_pages` | сколько страниц листать (по умолчанию 1) |
| `poll_interval_seconds` | собственный интервал опроса площадки в секундах; `0` — в каждом цикле |
| `proxy_strategy` | стратегия прокси площадки: `round_robin`, `sticky` или `none`; пусто — `network.proxy_strategy` |

`poll_interval_seconds` задаёт минимальную паузу между опросами конкретной
площадки поверх общего интервала цикла. В автоматических циклах площадка с
интервалом пропускается, пока время не истечёт (в лог пишется строка про
«пропущен по расписанию»); ручной запуск с `-p имя_площадки` расписание
минует и опрашивает немедленно. Для `kwork_ru` задано `1800` (2 раза в час):
частые однотипные визиты с одного IP антибот Qrator наказывает блоком на
часы, даже с человеческими паузами и прогревом сессии.

`proxy_strategy` управляет проксированием площадки (пул берётся из
`RU_PROXY_URLS` в `.env`). По умолчанию (`none` — значение
`network.proxy_strategy`) пул не задействован никем. Для `kwork_ru` задан
`sticky`: домен закрепляется за одним прокси-IP, куки прогрева и TLS-сессия
согласованы с ним; при остывании прокси после ошибок домен перепривязывается
к следующему доступному, а куки прогреваются заново. Пустой пул = прямой
запрос, поведение прежнее.

`detail_enrichment` присутствует в конфиге и модели, но в текущей реализации
адаптеры не делают дополнительный запрос карточки. Если вы включите его,
поведение не изменится, пока вы не реализуете обогащение в адаптере.

#### `scoring`

| Ключ | Смысл |
|---|---|
| `weights` | веса шести факторов |
| `red_flag_penalty` | множитель штрафа за красные флаги |
| `skill_match.skills` | навыки для пересечения |
| `skill_match.exclude_keywords` | нежелательные темы |
| `market_median_rub` | медианы бюджета по категориям |
| `assumed_hours_default` | запасная оценка часов |
| `freshness_half_life_hours` | период полураспада свежести |
| `competition.k` | параметр конкуренции |
| `client_quality.*` | веса качества заказчика |

Порогов `top_n`, `min_skill_match` и `min_total_score` больше нет: скоринг не
фильтрует заказы, а задаёт только порядок показа. Все заказы, прошедшие фильтр
категорий/подкатегорий и минимальной цены, показываются каждому подписчику;
заказы со штрафом за красные флаги и старые идут последними.

#### `red_flags`

Каждое правило имеет:

- `enabled` — включено ли;
- `severity` — сила 0..1;
- `patterns` — regex-шаблоны;
- специальные поля `budget_ratio_below`, `min_scope_chars`,
  `max_description_chars`.

Правила из примера:

| Код | Что ловит |
|---|---|
| `unpaid_test` | бесплатное тестовое задание |
| `offplatform_payment` | оплата вне безопасной сделки, на карту, после сдачи |
| `contact_before_hire` | просьба писать в Telegram/WhatsApp до найма |
| `scope_mismatch` | большой объём при бюджете ниже 25% медианы |
| `vague_brief` | описание короче 90 символов |
| `urgency_pressure` | «срочно сегодня», «нужно вчера» |

#### `llm`

| Ключ | Смысл |
|---|---|
| `enabled` | использовать LLM |
| `temperature` | температура генерации |
| `max_output_tokens` | лимит ответа |
| `timeout_seconds` | таймаут запроса |
| `fallback_enabled` | разрешить детерминированный fallback |
| `style.banned_phrases` | запрещённые фразы |
| `style.max_emoji` | максимум эмодзи |
| `style.max_exclamation` | максимум восклицательных знаков |
| `style.min_specificity_overlap` | минимум пересечения с ТЗ |

#### `messaging`

| Ключ | Смысл |
|---|---|
| `limits` | лимиты длины и ссылок по площадкам |
| `require_human_approval` | требовать подтверждение оператора |
| `max_sends_per_hour` | максимум отправок в час |
| `min_seconds_between_sends` | пауза между отправками |
| `max_messages_per_cycle` | сколько писем генерировать за цикл |

`max_messages_per_cycle` ограничивает только **генерацию писем**. Заказы сверх
лимита всё равно попадают в Telegram, но без готового текста.

#### `category_filter`

| Ключ | Смысл |
|---|---|
| `enabled` | включить фильтр |
| `categories` | список ключей рубрик Kwork; пусто = все |
| `subcategories` | выбранные категории внутри рубрики |
| `min_confidence` | минимальная уверенность классификатора |
| `unknown_policy` | `include` или `exclude` для неизвестных |
| `min_price_rub` | минимальная цена в рублях; заказы без цены (по договорённости) показываются всегда; 0 — выключено |

Фильтр активен только когда `enabled=true` **и** `categories` не пуст.
В Telegram настройка — `/categories`: сначала выбирается рубрика
(Дизайн, Разработка и IT, Тексты и переводы, SEO и трафик, Соцсети и
маркетинг, Аудио, видео, съемка, Бизнес и жизнь), затем в подменю рубрики —
конкретные категории. Мин. цена: `/categories price 5000` или кнопка
«💰 Мин. цена» в меню.

#### `fx_to_rub`

Курсы валют к рублю. Ключ необязателен: если его нет в YAML, используются
значения по умолчанию из модели `AppConfig`:
`RUB=1.0`, `UAH=2.30`, `USD=95.0`, `EUR=102.0`, `BYN=29.0`. Значения
ориентировочные; перед реальными решениями о ценах обновите их из надёжного
источника.

### 5.3. `.env`

Секреты живут только в `.env`; в `config.yaml` их быть не должно.

```dotenv
FREELANCE_BOT_ENV=dev
FREELANCE_BOT_CONFIG=config.yaml

TELEGRAM_BOT_TOKEN=
TELEGRAM_ADMIN_CHAT_IDS=

LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=
LLM_MODEL=gpt-4o-mini

CAPSOLVER_API_KEY=
TWOCAPTCHA_API_KEY=

RU_PROXY_URLS=

FREELANCE_BOT_DB=var/freelance.db
FREELANCE_BOT_OUTBOX=var/outbox
```

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от `@BotFather` |
| `TELEGRAM_ADMIN_CHAT_IDS` | id админов через запятую; добавлять новых можно прямо в боте командой `/adduser ID` |
| `LLM_BASE_URL` | база OpenAI-совместимого API |
| `LLM_API_KEY` | ключ; без него работает fallback |
| `LLM_MODEL` | имя модели |
| `CAPSOLVER_API_KEY` | ключ CapSolver |
| `TWOCAPTCHA_API_KEY` | ключ 2Captcha |
| `RU_PROXY_URLS` | прокси через запятую |
| `FREELANCE_BOT_DB` | путь к SQLite |
| `FREELANCE_BOT_OUTBOX` | каталог outbox |

`Secrets.telegram_admins` разбирает строку через запятую и оставляет только
числовые id; ведущий минус допускается, поэтому id группы тоже работает.
При проверке доступа смотрится и `effective_user.id`, и `effective_chat.id`.

### 5.4. `profile.yaml`

Профиль — это не секрет, а описание исполнителя. Он влияет на письма и цены.

```yaml
name: ""
experience_years: 3
location: "Россия"

skills:
  - Python
  - Telegram Bot API
  - FastAPI
  - PostgreSQL
  - Парсинг данных

secondary_skills:
  - JavaScript
  - HTML/CSS

experience_summary: |
  Разработал более 20 Telegram-ботов...

pricing:
  strategy: "markup"          # minimum | markup | llm_estimate
  markup_percent: 1.0
  min_acceptable_rub: 5000
  hourly_rate_rub: 2000
  include_price_in_message: false

message_style:
  tone: "friendly"            # professional | friendly | casual
  length: "medium"            # short | medium | long
  mention_portfolio: true
  ask_questions: true
  max_emoji: 0
  banned_phrases:
    - "я являюсь"
    - "как опытный"

availability:
  hours_per_week: 20
  immediate_start: true
  preferred_duration: "any"

communication:
  preferred_platforms: [telegram, email]
  typical_response_hours: 2
```

Стратегии цены:

- `minimum` — цена чуть ниже бюджета заказа, но не ниже
  `min_acceptable_rub`; если бюджета нет, берётся минимум.
- `markup` — бюджет × `markup_percent`, но не ниже минимума; если бюджета нет,
  берётся минимум (метка `markup-floor`).
- `llm_estimate` — `estimated_hours × hourly_rate_rub`; если LLM не дала часы,
  используется бюджет (метка `llm-estimate-fallback`), иначе минимум.

`profile.calculate_price()` — вспомогательный метод модели; рабочий конвейер
использует `MessageGenerator.resolve_price()`, потому что там есть метки
стратегий и дополнительные fallback-ветки.

### 6.6.1. `reclassify`

```bash
python -m freelance_bot.cli reclassify
python -m freelance_bot.cli reclassify --limit 500
```

Пересчитывает рубрику у уже сохранённых заказов по текущему классификатору.
Нужна после правок таксономии или сопоставления словоформ: старые записи
хранят результат прошлой версии, поэтому заказы без рубрики не попадали в
`/jobs` и в доставку.

Команда заново классифицирует сохранённый `payload` и обновляет
`category_key`, `category_group`, `subcategory`, а также признак `eligible`
по общему фильтру категорий и минимальной цены из `config.yaml`. Признак
`eligible` считается так же, как в конвейере: заказ подходит, если его
пропускает общий фильтр или он выбран хотя бы одним подписчиком в
`/filters`. Печатает счётчики: проверено, с рубрикой, без рубрики,
подходящих.

`--limit N` обрабатывает только последние N записей — удобно для пробного
прогона на большой базе.

## 7. Telegram-бот: настройка и эксплуатация

### 7.1. Создание бота

1. Откройте [@BotFather](https://t.me/BotFather).
2. Отправьте `/newbot`.
3. Задайте имя и username.
4. Скопируйте токен вида `1234567890:ABCdef...`.

### 7.2. Chat id

- Личный чат: напишите [@userinfobot](https://t.me/userinfobot), он покажет id.
- Группа: добавьте бота, отправьте сообщение и откройте
  `https://api.telegram.org/bot<TOKEN>/getUpdates`; `chat.id` группы
  отрицательный (например, `-1001234567890`). Отрицательные id поддерживаются:
  `Secrets.telegram_admins` принимает необязательный ведущий минус.

### 7.3. `.env`

```dotenv
TELEGRAM_BOT_TOKEN=1234567890:ABCdef...
TELEGRAM_ADMIN_CHAT_IDS=123456789
```

Несколько админов — через запятую. Пробелы вокруг id допустимы.

### 7.4. Проверка и запуск

```bash
python -m freelance_bot.cli telegram-check
python -m freelance_bot.cli telegram-check --send-test
python -m freelance_bot.cli telegram --interval 300 --top 10
```

При старте бот:

- создаёт `Application` с таймаутами 30 секунд;
- регистрирует команды и callback-обработчик;
- запускает polling с `drop_pending_updates=True`;
- входит в цикл: если пауза — ждёт 10 секунд; иначе запускает `run_cycle`;
- после цикла ждёт текущий интервал, который может меняться через `/interval`;
- по SIGINT/SIGTERM аккуратно останавливает бота и закрывает store.

### 7.5. Что приходит в Telegram

На каждый заказ, прошедший фильтры, отправляется карточка в формате эталона:

- шапка: иконка отрасли и бейдж «🟢 Новый»;
- заголовок заказа;
- первые 2–3 строки описания и строка «Показать полностью ▾», если текст
  длиннее;
- блок «💰 Бюджет»: сумма в валюте заказчика и подпись типа цены;
- блок «📅 Срок выполнения»: срок из задания или «по договорённости»;
- блок «👤 О заказчике»: имя, стаж на платформе, метка проверки и метрики
  (рейтинг, доля найма, число заказов). Если площадка не раскрыла данных,
  блок не показывается вовсе;
- строка «🌐 Биржа: {название} · ID заказа: #{id}» и время публикации;
- кнопки «🔗 Перейти на страницу заказа», «🪄 Составить письмо-ответ с AI»
  и «♥ Выделить как понравившееся» / «💔 Убрать из избранного».

Вторым сообщением приходит «💡 Полезно знать» — почему заказ подошёл под
профиль. В саму карточку балл, «Почему подходит», «Суть задачи», цена по
стратегии и черновик письма не попадают: письмо собирает AI-квиз.

### 7.5.1. AI-квиз «Письмо под заказ»

Кнопка «🪄 Составить письмо-ответ с AI» запускает диалог из четырёх шагов:
тон письма, акцент (опыт / план работ / скорость), упоминание денег и
уточняющий вопрос заказчику. На каждом шаге доступны готовые варианты и
«✍️ Свой вариант». Готовое письмо показывается целиком с кнопками
«✏️ Редактировать», «📋 Скопировать» и «🔄 Перегенерировать».

Черновик сохраняется в SQLite (`jobs.draft_text`), поэтому кнопки копирования
и правки работают и после рестарта бота. Ответы квиза живут в памяти процесса:
диалог короткий, а при потере ответов «Перегенерировать» вежливо начинает
квиз заново.

Если письмо не сгенерировано (LLM недоступен, цена ниже минимума), карточка
всё равно приходит — квиз сообщит об ошибке и предложит написать текст вручную.

Карточка доставляется **по личным фильтрам**: `pipeline` определяет получателей
(аудитория бота + сохранённые фильтры подписчиков) и вызывает
`telegram_bot.deliver_job(chat_ids, scored, ...)`. Факт доставки пишется в
`user_deliveries`; недоставленное (бот был выключен) повторяется в следующем
цикле.

### 7.6. Ограничения Telegram-слоя

- Максимум текста в сообщении — 4000 символов (запас от лимита Telegram 4096).
- Длинные сообщения делятся по границе строки или пробела; клавиатура
  крепится к последнему фрагменту.
- Динамический текст экранируется для legacy Markdown: `\`, `_`, `*`, `[`, `]`,
  backtick.
- Ошибка отправки одному админу не останавливает отправку остальным.
- Изменения через команды живут **в памяти процесса**. Для постоянного
  хранения редактируйте `config.yaml` и `profile.yaml`.

## 8. Telegram-команды и кнопки

### 8.1. Команды

Права: **(А)** — только супер-админ (чаты из `TELEGRAM_ADMIN_CHAT_IDS`),
**Все** — любой одобренный пользователь.

| Команда | Права | Поведение |
|---|---|---|
| `/start` | Все | приветствие и список команд; для нового пользователя — заявка на подписку (см. 8.2) |
| `/menu` | Все | компактный список всех команд по группам |
| `/help [команда]` | Все | справка по всем командам или подробно по одной |
| `/status` | Все | статус пайплайна и статистика последнего цикла |
| `/jobs [5\|10\|30]` | Все | сперва выбор биржи, затем последние заказы только с неё: балл, бюджет, ссылка |
| `/filters` | Все | меню личных фильтров: биржи, рубрики, подкатегории, мин. цена |
| `/filters platforms` | Все | выбор бирж inline-кнопками (пустой выбор = все) |
| `/filters price N` | Все | минимальная цена личного фильтра |
| `/filters reset` | Все | сброс личных фильтров к «показывать всё» |
| `/favorites` | Все | избранные заказы (кнопка ♥ на карточке) |
| `/settings` | А | включённые площадки, фильтр категорий, интервал |
| `/platforms` | А | inline-кнопки включения/выключения площадок |
| `/categories` | А | inline-кнопки фильтра и категорий |
| `/interval N` | А | интервал 600..3600 секунд |
| `/score` | А | штраф красных флагов и свежесть: `/score penalty 0.35`, `/score freshness 18` |
| `/pause` / `/resume` | А | приостановить/возобновить сбор |
| `/stats` | Все | статистика за 7 дней из SQLite |
| `/logs` | А | последние 10 ошибок из памяти (хранится до 50) |
| `/users` | А | кто имеет доступ: админы из `.env` (постоянные), добавленные через `/adduser`, и заявки на подписку в ожидании |
| `/adduser ID` | А | выдать доступ пользователю по его Telegram ID (сохраняется в SQLite, переживает рестарт) |
| `/deluser ID` | А | убрать доступ добавленного пользователя; админы из `.env` убираются только правкой `.env` |
| `/pricing` | А | выбор стратегии цены |
| `/markup N` | А | коэффициент наценки |
| `/minprice N` | А | минимальная цена |
| `/profile` | А | профиль, навыки, опыт |

Примеры:

```text
/interval 1800
/filters price 5000
/jobs 30
/markup 1.15
/markup 15
/minprice 8000
```

Порогов `/minscore` больше нет: заказы скрывают только фильтры (личные и общий
фильтр категорий), а не балл.

`/markup` принимает и множитель, и процент: если число больше 10, оно делится
на 100 и прибавляется к 1. Допустимый диапазон — от 0.01 до 5. Значение
сохраняется в памяти профиля, не в файле.

`/minprice` принимает число, пробелы и запятые удаляются. Отрицательное
значение отклоняется.

Кнопки `/menu` и `/help` закреплены под полем ввода: нажатие отправляет
команду, набирать её вручную не нужно. Список всех команд дополнительно
зарегистрирован в меню Telegram (кнопка «/»).

### 8.2. Подписка на бота

Доступ выдаётся по заявке:

1. Новый пользователь нажимает `/start` — создаётся заявка на подписку
   (таблица `bot_subscribers`, статус `pending`). Пользователь получает
   подтверждение со своим ID.
2. Админам приходит карточка заявки с именем, username и кнопками
   «✅ Одобрить» / «❌ Отклонить».
3. При одобрении пользователю приходит «Вы подписаны», его ID добавляется в
   `bot_admins` (как после `/adduser`): панель и карточки заказов доступны
   сразу и переживают рестарт.
4. При отклонении приходит «Заявка отклонена», доступ не выдаётся; повторный
   `/start` показывает «Заявка отклонена», новую заявку не создаёт.

`/users` дополнительно показывает заявки в ожидании одобрения. `/deluser`
помечает подписку отклонённой, чтобы исключённый не вернулся повторным
`/start`. Пользователя без заявки всё ещё можно добавить вручную: `/adduser ID`.

### 8.3. Callback-кнопки

| Префикс / данные | Действие |
|---|---|
| `platform_toggle_<name>` | переключить площадку (общий сбор, админ) |
| `category_filter_toggle` | включить/выключить фильтр категорий (админ) |
| `category_toggle_<key>`, `cat_top_/cat_all_/cat_grp_/cat_sub_/cat_price/cat_menu` | меню общего фильтра категорий (админ) |
| `uf_menu`, `uf_top_/uf_all_/uf_grp_/uf_sub_/uf_platform_/uf_platforms/uf_price/uf_reset` | меню личных фильтров `/filters` |
| `fav:<uid>` / `unfav:<uid>` | добавить/убрать заказ в избранном; кнопка переворачивается на месте |
| `send:` / `copy:` / `skip:` | отправить письмо / скопировать текст / убрать кнопки карточки |
| `pricing_strategy_<strategy>` | выбрать `minimum`, `markup`, `llm_estimate` (админ) |
| `sub_approve:<chat_id>` | одобрить заявку на подписку |
| `sub_reject:<chat_id>` | отклонить заявку на подписку |
| `approve_<job_uid>` / `reject_<job_uid>` | устаревшие кнопки: бот отвечает предупреждением о миграции на новые |

Личные callback'и (`uf_`, `fav:`, `unfav:`, карточные `send:/copy:/skip:`)
пишут только в данные самого пользователя или его карточку; общие настройки
защищены супер-админом.

### 8.4. Права доступа

Каждая команда и каждый callback проверяют права. Два уровня:

- **Супер-админ** — `effective_user.id`/`effective_chat.id` входит в
  `admin_chat_ids` из `.env`: полный доступ, включая общие настройки
  (`/interval`, `/score`, `/platforms`, `/categories`, `/set`, `/reset`).
- **Одобренный пользователь** — запись в `bot_admins` (через `/adduser` или
  одобрение заявки): личные команды (`/filters`, `/favorites`, `/jobs`) и
  карточки заказов.

Посторонним бот отвечает «⛔ У вас нет доступа к этому боту.» и ничего не
меняет. Исключение — `/start`: он доступен всем и для посторонних запускает
заявку на подписку (см. 8.2).

## 9. Конвейер: `pipeline.py`

### 9.1. `collect()`

```python
async def collect(config, secrets, *, platform_names=None, with_browser=True)
    -> tuple[list[Job], list[PlatformRunResult], AdapterContext]
```

Шаги:

1. `build_adapters(config)` создаёт экземпляры включённых площадок.
2. Если передан `platform_names`, остаются только они.
3. `build_context()` собирает HTTP-клиент, прокси, robots, браузер и решатель.
4. Адаптеры обрабатываются **последовательно**. Это сделано намеренно:
   доменные лимиты уже сериализуют большую часть работы, а падение одного
   адаптера не должно ломать остальные.
5. Для каждого `RawJob` вызывается `normalise`.
6. Ошибка нормализации логируется, но не роняет цикл.
7. `result.jobs_found` заменяется на число успешно нормализованных заказов.

### 9.2. `run_cycle()`

```python
async def run_cycle(config, secrets, *, platform_names=None,
                    with_browser=True, generate_messages=True, only_new=True,
                    store=None, telegram_bot=None, profile=None) -> CycleReport
```

Порядок:

1. Создаёт `CycleReport` и `JobStore`, если store не передан.
2. Собирает заказы.
3. Дедуплицирует внутри цикла по `uid`, оставляя заказ с самым длинным
   описанием.
4. Если фильтр категорий активен, классифицирует каждый заказ и отбрасывает
   непрошедшие.
5. `ScoringEngine.rank(unique)` оценивает **все** заказы; `eligible()` всегда
   True — порогов больше нет.
6. Определяет `previously_seen` по SQLite.
7. Сохраняет **все** заказы, а не только показанные. Иначе заказ, стоявший
   11-м, каждый цикл снова считался бы новым.
8. `new_uids` — новые заказы, по которым ещё нет показа.
9. `candidates` — новые заказы, отсортированные по приоритету показа:
   сначала без штрафа за красные флаги, внутри — по свежести
   (`published_at DESC`).
10. `report.top` — кандидаты в порядке показа.
11. Создаёт `MessageGenerator` и `OutboxSender`.
12. Делит кандидатов на `with_letter` (первые `max_messages_per_cycle`) и
    `without_letter`.
13. Запускает обработку с семафором на 3 одновременные задачи.
14. В `handle`:
    - генерирует анализ и письмо, если `draft=True`;
    - считает цену;
    - если цена ниже минимума — письмо отбрасывается;
    - сохраняет сообщение в SQLite;
    - отправляет через `OutboxSender`;
    - при успехе увеличивает `messages_sent`, иначе `messages_rejected` и
      обнуляет письмо, чтобы не предлагать его к одобрению;
    - доставляет заказ подписчикам: определяет получателей по личным фильтрам
      (`all_user_filters` + аудитория бота) и вызывает
      `telegram_bot.deliver_job(chat_ids, scored, ...)`; факт доставки
      сохраняется в `user_deliveries` — недоставленные заказы будут повторены.
15. После `gather` отправляет сводку цикла.
16. Сохраняет цикл в SQLite.
17. Закрывает HTTP и браузер.
18. В `finally` закрывает store, если владел им.

### 9.3. `run_trial()`

Включает `dry_run`, крутит циклы до дедлайна, спит `min(interval, remaining)`,
возвращает список отчётов. В `finally` восстанавливает исходный `dry_run`.

### 10.2. `normalize.py`

`parse_money(text)` возвращает `(amount, currency, kind)`:

- распознаёт `₽`, `руб`, `$`, `USD`, `€`, `EUR`, `грн`, `UAH`, `BYN`;

ориентировочная дневная ставка. Это не точная бухгалтерия, а сигнал для
скоринга.

## 11. Скоринг и красные флаги

### 11.1. Формула

```text
contribution_i = raw_i * weight_i / sum(weights)
base = sum(contribution_i)
penalty = min(0.8, severity_sum * red_flag_penalty)
total = round(100 * base * (1 - penalty), 1)
```

Веса нормализуются во время работы, поэтому их сумма не обязана быть равна 1.
Меняя один вес, вы не обязаны пересчитывать остальные.

### 11.2. Шесть факторов

#### `budget`

- Если бюджета нет или медиана <= 0: `raw = 0.40`, нейтральная оценка.
- Иначе `ratio = estimate / median`.
- `ratio` интерполируется по точкам:
  `(0, 0.02)`, `(0.25, 0.15)`, `(0.5, 0.45)`, `(0.8, 0.75)`,
  `(1.5, 1.0)`, `(100, 1.0)`.
- В объяснении указывается, выше или ниже медианы бюджет.

#### `skill_match`

- Заголовок, категория и заявленные навыки — более сильный сигнал, чем текст.
- `title_matched` — совпадения в заголовке/категории/навыках.
- `body_matched` — совпадения в описании без контактов и ссылок.
- Если найдено исключённое слово: `raw = 0.10`.
- Если есть совпадения в заголовке: `raw = clamp(0.55 + 0.12 * len(matched))`.
- Если только в описании: `raw = clamp(0.32 + 0.08 * len(body_matched))`.
- Если ничего: `raw = 0.20`.

Именно этот фактор отсекает заказы, где случайно совпало одно слово.

#### `client_quality`

Учитывает доступные сигналы:

- hire rate;
- траты относительно `spend_reference_rub`;
- верификацию;
- рейтинг и число отзывов.

Если данных нет — `raw = 0.50`. Если есть — взвешенное среднее по доступным
компонентам.

#### `competition`

```text
raw = 1 / (1 + proposals / k)
```

При `k = 10`: 0 откликов → 1.0, 10 → 0.5, 20 → 0.33. Если число откликов
неизвестно — `raw = 0.60`.

#### `freshness`

```text
raw = 0.5 ** (age_hours / half_life_hours)
```

По умолчанию half-life 18 часов. Если дата неизвестна — `raw = 0.50`.

#### `urgency_fit`

- Дедлайна нет: `0.60` для срочных, `0.50` иначе.
- Срок истёк: `0.10`.
- <= 24 часов: `1.0`.
- <= 72 часов: `0.80`.
- Больше: `0.55`.

### 11.3. Красные флаги

`redflags.detect()` ищет regex-шаблоны в `title + description`, приводит к
нижнему регистру. Для `scope_mismatch` дополнительно сравнивает бюджет с
медианой и требует достаточно длинное описание. Для `vague_brief` — короткое
описание.

`severity_sum` складывает флаги с убывающей отдачей:

```text
total = sum(severity_i * 0.75**i)  # флаги отсортированы по убыванию
total = min(total, 2.4)
```

Это не даёт множеству мелких флагов перевесить один серьёзный.

### 11.4. Допуск к показу

Порогов допуска (`min_total_score`, `min_skill_match`) больше нет:
`ScoringEngine.eligible()` всегда возвращает True. Заказы скрываются только
фильтрами — общими (категории/подкатегории, мин. цена из `category_filter`)
и личными фильтрами подписчиков (`user_prefs.py`). Скоринг влияет лишь на
порядок: заказы без штрафа и свежие показываются первыми, со штрафом —
последними.

### 11.5. Объяснимость

У каждого фактора есть `rationale` на русском. `summary_ru` собирает два
сильнейших фактора, слабое место, красные флаги и размер штрафа. Это же
показывается в таблице `score`, в карточке Telegram и в `report`.

### 12.2. Классификация

`classify_job(job)`:

- собирает три поля: `title`, `meta` (категория + навыки), `description`;
- взвешивает совпадения: заголовок 3.0, meta 2.5, описание 1.0;
- группа даёт вес 0.8, лист — 1.0, дополнительные ключевые слова — 0.7;
- выбирает категорию с максимальным баллом;
- внутри категории выбирает лучшую группу и подкатегорию;
- `confidence = min(1.0, score / 3.0)`;
- при равенстве побеждает категория, идущая раньше в таксономии.

`contains_term` из `text.py` использует границы слов и основы для русских
терминов: `сайт` находит `сайта`, `сайтов` и `сайтами`, `дизайн` — `дизайнера`,
`парсинг` — `парсинга`. Границы слова обязательны: `бот` не находится внутри
`работа`.

Основа получается отсечением падежного окончания (`-ами`, `-ого`, `-ая`,
`-ов`, `-а`, `-и`, ...). После основы допускается короткий хвост окончания,
поэтому формы одного слова совпадают без ложных срабатываний.

Дефис считается разделителем слов так же, как пробел: `сайт-визитка`,
`сайт визитка` и `сайта-визитки` — одна фраза. Без этого дефисное слово
было единым токеном и не совпадало ни с одной словоформой.

Составные фразы, смысл которых ломается при подсчёте по отдельным словам,
распознаются целиком (`PHRASE_ALIASES` в `categories.py`) и сразу задают
рубрику:

- `сайт-визитка`, `сайт визитка`, `сайт-визитку` → «Создание сайтов» /
  «Новый сайт»;
- `сайт-лендинг` → «Создание сайтов» / «Новый сайт»;
- `интернет-магазин`, `интернет магазин` → «Создание сайтов» /
  «Новый сайт».

Причина: слово «визитка» внутри «сайт-визитка» совпадало с листом «Визитки»
из дизайна (печатная полиграфия) и перетягивало заказ в дизайн. Печатные
визитки при этом остаются в дизайне — правило срабатывает только на фразе
целиком.

У правила есть исключения (`blockers`): если интернет-магазин — лишь объект
чужой работы, рубрика не меняется. «Реклама интернет-магазина», «настройка
Google Ads», «UX/UI-дизайнер для интернет-магазина», «обработка изображений
для интернет-магазина» остаются в продвижении или дизайне. «Редизайн
интернет-магазина» и «доработка» — по-прежнему работа по сайту.

### 12.4. Разработка против продажи готового

В рубрике «Бизнес» есть группа «Продажа сайтов и групп» с листом
«Приложения» — это продажа готовых активов. Названия листьев совпадают со
словами заказов на разработку, поэтому «Создать мобильное приложение»
уходило в бизнес, а слово «визитка» в «сделать демо-бота (визитка)» — в
полиграфию.

Правило разделяет по намерению:

- «создать / сделать / разработать / доработать / нужен / ищу» + «приложение»
  или «бот» → «Разработка и IT»;
- «мобильное приложение», «веб-приложение», «приложение для Android»
  → «Разработка и IT» без глагола: такой объект нельзя «продать»;
- «продать», «купить», «готовый», «в аренду» → остаётся в бизнесе;
- «приложение (каталог продукции) для врачей» без глагола разработки
  остаётся в бизнесе.

### 12.3. Фильтр

`CategoryFilter.active` истинно только при `enabled=True` и непустом списке
категорий.

`allows(classification)`:

1. Если фильтр неактивен — пропустить.
2. Если категория неизвестна — пропустить только при
   `unknown_policy="include"`.
3. Если `confidence < min_confidence` — аналогично.
4. Если категория не входит в список — отклонить.
5. Если для категории заданы подкатегории — совпадение должно быть по
   подкатегории или группе (нормализованно).
6. Если лист не определён, но рубрика выбрана — пропустить. Классификатор
   не всегда находит конкретную подкатегорию («Создание сайта» даёт рубрику
   без листа); отбрасывать такой заказ нельзя, иначе он молча теряется.

Выбор подкатегорий расширяется внутри «семьи» сайтовых работ: `Доработка и
настройка сайта`, `Создание сайтов` и `Верстка` — одна работа для заказчика.
Если пользователь выбрал хотя бы одну категорию из этой семьи, остальные
входят в выбор автоматически: «выбрана веб-верстка» больше не теряет
«создание сайта».

### 12.4. Сбор шире админского фильтра

Общий фильтр `category_filter` задаёт, что видит администратор, но он не
отменяет выбор подписчиков. Заказ проходит сбор, если его пропускает общий
фильтр **или** он подходит хотя бы одному подписчику с явно выбранными
рубриками (`user_filters.categories` непустой).

Пример: админ собирает только `programming`, подписчик в `/filters` выбрал
«Тексты и переводы». Текстовые заказы сохраняются и доходят до этого
подписчика — раньше общий фильтр отсекал их до применения личных фильтров,
и выбор в `/filters` молча не работал.

Фильтр без ограничений у подписчика (`categories: []`) сбор не расширяет:
он означает «всё, что прошло общий фильтр».

Доставка считается по чату: `mark_notified` отмечает заказ показанным в
админской ленте, а `user_deliveries` помнит, каким чатам карточка уже ушла.
Поэтому заказ получает каждый подписчик, чьим фильтрам он подходит, и
повторный проход не дублирует доставленное.

## 13. Адаптеры площадок

### 13.1. Контракт `BaseAdapter`

Каждый адаптер задаёт:

```python
class MyAdapter(BaseAdapter):
    platform = "my_site"
    domain = "example.ru"
    transport = TransportKind.HTTP   # или BROWSER
    wait_selector = "div.card"       # только для browser
    prewarm_path = "/"               # только для browser

    def parse(self, html: str, base_url: str) -> list[RawJob]:
        ...
```

`BaseAdapter.fetch(ctx)`:

1. Проверяет robots.txt.
2. Листает страницы до `max_pages`.
3. Для `http` вызывает `ctx.http.get()`.
4. Для `browser` — `ctx.browser.fetch()`.
5. Если получен `OK`/`EMPTY`, вызывает `parse`.
6. Ошибка парсинга превращается в `PARSE_ERROR`, но не роняет цикл.
7. Если HTTP получил `CHALLENGE`/`BLOCKED`, делается одна попытка через
   браузер (если браузер доступен).
8. Останавливается при пустой странице или достижении
   `max_jobs_per_platform`.
9. Возвращает `(jobs, PlatformRunResult)`.

`parse` обязан не падать на пустом или мусорном HTML: лучше вернуть `[]`.

### 13.2. Включённые площадки

| Площадка | Транспорт | Карточки | Особенности |
|---|---|---|---|
| `fl_ru` | HTTP | `div.b-page__lenta_item.b-post` | DDoS-Guard на краю, без JS-challenge на листинге |
| `freelance_ru` | HTTP | `article.task-card` | Inertia-подобная разметка, первая страница в HTML |
| `freelancejob_ru` | HTTP | `div.x17` | обычный серверный HTML |

### 13.3. Как добавить новую площадку

1. Снимите публичную страницу через `tools/capture.py` (HTTP) или
   `tools/browser_probe.py` (браузер).
2. Сохраните HTML в `fixtures/live/`.
3. Напишите адаптер: `platform`, `domain`, `transport`, `wait_selector`,
   `parse`.
4. Зарегистрируйте его в `adapters/registry.py`:

```python
from .my_site import MySiteAdapter

ADAPTERS: dict[str, type[BaseAdapter]] = {
    ...
    MySiteAdapter.platform: MySiteAdapter,
}
```

5. Добавьте площадку в `config.yaml`:

```yaml
platforms:
  my_site:
    enabled: true
    transport: http
    listing_url: "https://example.ru/projects/"
    detail_enrichment: false
    notes: "Проверено 2026-11, серверный HTML."
    max_pages: 1
```

6. Добавьте лимит сообщений в `messaging.limits`, если его нет.
7. Добавьте фикстуру в `tests/conftest.py::FIXTURE_MAP`.
8. Напишите тест в `tests/test_parsers.py`: точное число карточек и конкретные
   поля, а не просто «что-то вернулось».
9. Запустите `pytest`, `ruff`, `mypy`.

### 13.4. Отладка селекторов

```bash
python -m freelance_bot.cli parse-fixture my_site fixtures/live/my_site.html
python -m freelance_bot.cli run --platform my_site --no-browser --top 5 -v
```

Если карточек 0:

- проверьте, что `parse` ищет правильный контейнер;
- проверьте, не изменился ли URL-паттерн;
- проверьте, не отдаёт ли сайт challenge вместо HTML;
- сохраните свежую фикстуру и сравните с прежней.

## 14. Сетевой слой

### 14.1. `StealthHttpClient`

- Один `AsyncSession` на каждый профиль имперсонации.
- Профили: `chrome131`, `chrome124`, `chrome120`, `safari17_0`, `edge101`.
- Заголовки: User-Agent, Accept, Accept-Language, Sec-Fetch-*, Sec-CH-UA.
- Перед запросом ждёт токен домена.
- Берёт прокси из пула, если он есть.
- Классифицирует ответ.
- Повторяет только `rate-limited` и сетевые ошибки, с backoff.
- На challenge/blocked возвращает результат без слепых повторов: решение об
  эскалации принимает адаптер.
- При успехе сообщает прокси об успехе, при ошибке — об ошибке.
- `close()` закрывает сессии.

### 14.2. Классификация ответа

`classify_response(status, headers, text)`:

- `429`, `439`, `403`, `503`, `>=500` → ищет подписи защитных слоёв;
- `429` без подписи → `BLOCKED`, `rate-limited`;
- `>=500` без подписи → `NETWORK_ERROR`, `upstream-error`;
- иначе `BLOCKED`, `http-forbidden`;
- подписи Cloudflare, DDoS-Guard, Qrator, Yandex SmartCaptcha, DataDome,
  Akamai, Variti → `CHALLENGE` или `BLOCKED`;
- `cf-mitigated: challenge` → Cloudflare;
- HTML короче 1200 символов с полем пароля/текстом входа → `LOGIN_WALL`;
- текст короче 400 символов → `EMPTY`;
- иначе `OK`.

### 14.3. Лимиты и backoff

`AsyncTokenBucket` — один на домен. `DomainLimiter.wait()` ждёт токен и добавляет
случайную паузу 0.35–1.4 секунды.

`backoff_delay(attempt, cfg)`:

```text
raw = min(base_seconds * 2**attempt, max_seconds)
delay = uniform(raw * 0.5, raw)  # при jitter=True
```

### 14.4. Прокси

`ProxyPool`:

- `round_robin` — следующий доступный;
- `sticky` — по домену (в текущей реализации acquire всё равно идёт по кругу,
  стратегия хранится для совместимости);
- `none` — без прокси;
- при ошибке прокси уходит в cooldown с экспоненциальной задержкой до 1 часа;
- `redact()` скрывает логин/пароль в логах;
- `healthy_snapshot()` отдаёт состояние без секретов.

### 14.5. robots.txt

`RobotsCache`:

- загружает `https://<domain>/robots.txt`;
- кеширует по домену;
- парсит только `200` и не-HTML;
- если robots.txt недоступен — fail-open («политика не опубликована»);
- если политика запрещает путь — `DISABLED` с причиной.

### 14.6. Браузер

`BrowserFetcher`:

- лениво запускает Playwright Chromium;
- один изолированный контекст на домен;
- stealth-JS убирает базовые признаки автоматизации;
- блокирует изображения, медиа и шрифты;
- делает prewarm на главной, чтобы получить обычные cookies;
- ждёт `wait_selector` до 15 секунд;
- ждёт `settle_ms`;
- делает правдоподобные движения мышью;
- классифицирует HTML;
- при challenge пытается решить CAPTCHA и внедрить токен;
- закрывает страницу в `finally`.

### 14.7. CAPTCHA

`CaptchaSolver` поддерживает:

- CapSolver: `createTask` + `getTaskResult`;
- 2Captcha: `in.php` + `res.php`;
- типы: `recaptcha_v2`, `hcaptcha`, `yandex_smartcaptcha`.

Токен не кешируется между сессиями. Ключи не логируются. При таймауте
выбрасывается `CaptchaError`, и браузерный слой возвращает исходный challenge.

## 15. LLM: анализ, письмо, guard, fallback

### 15.1. Клиент

`LLMClient` — минимальный OpenAI-совместимый клиент:

- POST `{base_url}/chat/completions`;
- `Authorization: Bearer <key>`;
- сообщения system + user;
- `temperature`, `max_tokens`;
- при `json_mode` добавляет `response_format={"type": "json_object"}`;
- ошибки HTTP и формы ответа превращаются в `LLMError`;
- `parse_json_loose` снимает code fences и вытаскивает объект из лишнего текста.

### 15.2. Промпт анализа

`analysis_prompt()` передаёт:

- профиль (имя, опыт, локация, навыки, занятость, связь);
- только релевантные заказу навыки;
- домен задачи;
- правила цены;
- стиль письма;
- запрещённые фразы;
- заголовок, бюджет, категорию, дедлайн, отклики, навыки, описание.

Модель должна вернуть JSON:

```json
{
  "need_summary_ru": "1-2 предложения",
  "requirements": ["..."],
  "deliverables": ["..."],
  "risks": ["..."],
  "questions_to_ask": ["..."],
  "skill_match": ["..."],
  "estimated_hours": 12,
  "suggested_price_rub": 24000,
  "first_message": "готовое письмо"
}
```

### 15.3. Генерация

`MessageGenerator.generate(job)`:

1. `analyse(job)` — LLM или эвристика.
2. Если черновика нет:
   - при `fallback_enabled=False` — `LLMError`;
   - иначе — детерминированный fallback.
3. `guard.check()`.
4. Если есть нарушения и источник `llm` — один repair-запрос.
5. Повторная проверка.
6. Если нарушения остались и fallback разрешён — генерируется fallback; если у
   него меньше нарушений, он заменяет LLM-текст.
7. Возвращается `GeneratedMessage` с `violations` и `source`.

### 15.4. Guard

Проверяет:

- пустое сообщение;
- длину по лимиту площадки;
- ссылки и внешние контакты (если `allow_links=False`);
- запрещённые фразы из конфига и профиля;
- AI-tells: «в современном мире», «стоит отметить», «под ключ» и т. п.;
- шаблонные формулировки;
- «воду»;
- эмодзи больше `max_emoji`;
- восклицательные знаки больше `max_exclamation`;
- долю кириллицы меньше 0.55;
- шаблонное начало;
- недостаточную конкретику (пересечение значимых токенов с заголовком и первыми
  400 символами ТЗ);
- больше двух вопросов;
- маркированный список;
- нумерованный список из 3+ пунктов;
- 4+ длинных тире.

Нарушения не выбрасывают сообщение молча: они сохраняются в БД и в outbox,
но `OutboxSender` блокирует отправку.

### 15.5. Fallback

Детерминированный генератор:

- чистит заголовок и детали от ссылок, ников, email, эмодзи;
- убирает повтор заголовка;
- выбирает подход по сигналам заказа: Telegram-бот, парсинг, веб, AI, данные,
  бэкенд, DevOps, автоматизация, интеграция, сервис, дизайн, текст;
- добавляет подходящие навыки профиля;
- добавляет цену, если `include_price_in_message`;
- задаёт один уточняющий вопрос;
- убирает восклицательные знаки.

Это не «заглушка ради теста»: текст должен быть пригоден к отправке, если LLM
недоступна.

## 16. Отправка, outbox и SQLite

### 16.1. Режимы

| Режим | Что делает |
|---|---|
| `dry-run` | пишет Markdown-файл и JSONL, ничего не отправляет |
| `assist` | ставит в очередь оператору, создаёт артефакт для копирования |
| `live` | требует `approved=True`, транспорт и rate gate |

По умолчанию проект работает в `dry-run`. `--live` снимает флаг, но не
добавляет транспорт. Без транспорта `send()` возвращает `ok=False`,
`mode="blocked"` и ничего не пишет. Это сделано специально, чтобы «живой» режим
не отправлял случайно.

### 16.2. Артефакты

```text
var/outbox/
  messages.jsonl
  2026-11-03/
    fl_ru__fl_ru_5525021.md
```

Markdown-файл содержит заголовок, платформу, ссылку, бюджет, число откликов,
режим, источник текста, результат проверок и сам текст письма.

`messages.jsonl` — append-only лог: время, `message_id`, `job_uid`, платформа,
заголовок, URL, текст, источник, модель, `dry_run`, `approved`, `delivered`.

### 16.3. RateGate

- не больше `max_sends_per_hour` за скользящий час;
- не чаще `min_seconds_between_sends`;
- запись времени отправки — только после успешного транспорта.

### 16.4. SQLite

Схема:

```sql
jobs(
  uid TEXT PRIMARY KEY,
  platform TEXT,
  external_id TEXT,
  url TEXT,
  title TEXT,
  budget_rub REAL,
  score REAL,
  first_seen TEXT,
  last_seen TEXT,
  payload TEXT
)

messages(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  job_uid TEXT,
  platform TEXT,
  text TEXT,
  source TEXT,
  model TEXT,
  violations TEXT,
  approved INTEGER,
  sent_at TEXT,
  created_at TEXT,
  UNIQUE(job_uid, text)
)

cycles(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at TEXT,
  finished_at TEXT,
  dry_run INTEGER,
  report TEXT
)

user_filters(
  chat_id INTEGER PRIMARY KEY,
  platforms TEXT,          -- JSON-список бирж
  categories TEXT,         -- JSON-список рубрик
  subcategories TEXT,      -- JSON-словарь: рубрика -> список подкатегорий
  min_price_rub REAL,      -- 0 = не задана (показывать всё)
  updated_at TEXT
)

user_favorites(
  chat_id INTEGER,
  job_uid TEXT,
  created_at TEXT,
  UNIQUE(chat_id, job_uid)
)

user_deliveries(
  chat_id INTEGER,
  job_uid TEXT,
  delivered_at TEXT,
  UNIQUE(chat_id, job_uid)
)
```

Важные детали:

- `upsert_job` возвращает `True`, если заказ новый.
- `save_message` использует `INSERT OR IGNORE`; при повторе возвращает id
  существующей записи.
- `pending_messages` выбирает `sent_at IS NULL` и `approved IS NULL OR approved=0`.
- `approve`/`reject` меняют флаг.
- `mark_sent` ставит `sent_at` и `approved=1`.
- `stats_since(days)` считает заказы, сообщения, отправки и отклонения за окно.
- `set_user_filters` поддерживает частичное обновление: поля, переданные как
  `None`, сохраняют прежнее значение; пустые списки очищают выбор.
- `user_jobs(prefs, limit)` применяет личные фильтры в Python и сортирует
  выдачу: заказы без штрафа первыми, внутри — по свежести.
- `mark_delivered_to`/`delivered_to` помнят, кому заказ уже показан: при
  недоступном боте доставка повторится в следующем цикле.
  `total_jobs` и `total_new` в текущей реализации совпадают.
- `JobStore` использует `RLock` и `check_same_thread=False`, поэтому один store
  можно передавать в асинхронные задачи.

## 19. Эксплуатация и диагностика

### 19.1. Почему заказ не пришёл в Telegram

Проверяйте по порядку:

1. Площадка включена в `config.yaml`?
2. `run`/`telegram` запущен с нужными `--platform`?
3. Фильтр категорий включён и заказ не попал в категорию?
4. `min_confidence` слишком высокий?
5. `unknown_policy="exclude"` отбросил неизвестный заказ?
6. Личный фильтр пользователя скрывает биржу/рубрику или бюджет ниже его
   минимальной цены? Проверьте через `/filters`.
7. Заказ уже был виден в предыдущем цикле и `only_new=True`?
8. По заказу уже есть сообщение в SQLite?
9. Заказ попал за `max_messages_per_cycle`? Тогда он должен прийти без письма.
10. Цена ниже `min_acceptable_rub`? Письмо отбрасывается, но карточка должна
    прийти.
11. Бот не запущен или пользователь не одобрен?

### 19.2. Почему нет письма

- LLM недоступна и `fallback_enabled=False`;
- guard нашёл нарушения, repair не помог, fallback тоже не лучше;
- цена ниже минимума;
- `generate_messages=False`;
- заказ сверх лимита писем.

### 19.3. Почему `--live` ничего не отправил

Это ожидаемо. В проекте нет транспорта, а `require_human_approval=True`.
`OutboxSender.send()` без `approved=True` и без транспорта возвращает
`blocked`. Штатный путь — dry-run/assist: проверить артефакт и отправить
вручную.

### 19.4. Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `playwright is not installed` | не установлен extra `browser` | `pip install -e ".[browser]"` и `playwright install chromium` |
| `TELEGRAM_BOT_TOKEN not configured` | пустой `.env` | заполнить токен |
| `TELEGRAM_ADMIN_CHAT_IDS not configured` | нет админов | указать id |
| Telegram `Unauthorized` | неверный токен | перевыпустить у BotFather |
| `LLM HTTP 401` | неверный ключ | проверить `LLM_API_KEY` |
| `LLM returned empty content` | провайдер вернул пусто | сменить модель/провайдера |
| пустой парсинг | изменилась вёрстка | снять фикстуру, обновить селекторы |
| `challenge`/`blocked` | антибот | включить браузер, прокси, решатель |
| `database is locked` | несколько процессов пишут в один файл | не запускайте два бота на одной БД |
| UnicodeEncodeError в консоли | cp1251 | `PYTHONIOENCODING=utf-8` |
| дубликаты писем | разный текст или сброс БД | проверить `UNIQUE(job_uid, text)` |

### 19.5. Обслуживание

- Раз в месяц переснимайте фикстуры и прогоняйте тесты.
- Раз в квартал обновляйте `fx_to_rub` и `market_median_rub`.
- Следите за браузерными площадками: они ломаются первыми.
- Проверяйте robots.txt и условия площадок перед включением новой.
- Не коммитьте `.env`.
- Делайте резервную копию `var/freelance.db`, если история важна.
- Ротируйте ключи LLM/CAPTCHA и прокси.

## 20. Ограничения проекта

- Вёрстка публичных площадок меняется без предупреждения. Тесты на фикстурах
  делают поломку видимой, но не предотвращают её.
- Браузерные площадки могут требовать резидентный IP и решатель CAPTCHA.
- Данные о заказчике на большинстве площадок скудные; скоринг оценивает их
  нейтрально, а не выдумывает.
- `detail_enrichment` зарезервирован, но не реализован в адаптерах.
- Автоматическая отправка на площадки намеренно не реализована.
- `freelancehunt_com` — украинская биржа с бюджетами в UAH; конвертация в RUB
  ориентировочная.
- `avito_ru` выключен по умолчанию: Qrator отдаёт 439 дата-центрам.
- `trial` и `dry-run` не проверяют реальную доставку; для неё нужен транспорт.

## 21. Учебный план: как повторить такой проект

Если вы хотите научиться делать подобных ботов, идите слоями.

### Урок 1. Модели и нормализация

- Опишите `RawJob` и `Job`.
- Напишите `parse_money`, `parse_relative_time`, `parse_absolute_time`.
- Сделайте тесты на русские форматы сумм и дат.

### Урок 2. Один HTTP-адаптер

- Возьмите одну серверную площадку.
- Снимите HTML.
- Напишите `parse` на BeautifulSoup.
- Сделайте `parse-fixture` и тест на точное число карточек.

### Урок 3. Сеть и вежливость

- Добавьте robots.txt.
- Добавьте token bucket на домен.
- Добавьте таймауты и backoff.
- Классифицируйте ответы: `ok`, `empty`, `challenge`, `blocked`.

### Урок 4. Скоринг

- Реализуйте 2–3 фактора.
- Сделайте объяснение на русском.
- Добавьте порог допуска.
- Напишите тесты на границы.

### Урок 5. LLM и защита

- Сделайте OpenAI-совместимый клиент.
- Попросите строгий JSON.
- Напишите guard: длина, ссылки, AI-tells, конкретика.
- Добавьте fallback на случай недоступности модели.

### Урок 6. Хранение и дедупликация

- SQLite: `jobs`, `messages`, `cycles`, `user_filters`, `user_favorites`, `user_deliveries`.
- `uid` = платформа + external_id.
- `UNIQUE(job_uid, text)` для сообщений.
- Сохраняйте все заказы, а не только показанные: иначе «невидимые» заказы
  выглядят новыми в каждом цикле.

### Урок 7. Telegram

- Создайте бота.
- Разделите права: супер-админ (чаты из `.env`) и обычные пользователи.
- Личные фильтры, избранное и доставка карточек — в SQLite на chat_id.
- Добавьте `/status`, `/stats`, `/pause`, `/resume`, `/filters`, `/favorites`.
- Экранируйте Markdown и делите длинные сообщения.

### Урок 8. Эксплуатация

- Логи.
- Preflight.
- Ограничения скорости.
- Резервные копии.
- Тесты на фикстурах.
- Документация.

## 22. Глоссарий

| Термин | Значение |
|---|---|
| `RawJob` | сырой заказ от адаптера |
| `Job` | нормализованный заказ |
| `uid` | `platform:external_id` |
| `Outcome` | результат загрузки площадки |
| `challenge` | антибот-проверка |
| `transport` | HTTP или браузер |
| `dry-run` | режим без отправки |
| `outbox` | каталог с артефактами писем |
| `guard` | проверка качества письма |
| `fallback` | детерминированное письмо без LLM |
| `red flag` | признак рискованного заказа |
| `eligible` | заказ, прошедший фильтры (порогов больше нет) |
| `user_filters` | личные фильтры подписчика (SQLite) |
| `personal delivery` | доставка заказа по личным фильтрам в его чат |
| `category_filter` | фильтр по таксономии Kwork |
| `robots.txt` | политика обхода сайта |
| `token bucket` | алгоритм ограничения частоты |
| `impersonation` | имитация TLS-отпечатка браузера |
| `CAPTCHA solver` | внешний сервис решения капчи |
| `PTB` | python-telegram-bot |
